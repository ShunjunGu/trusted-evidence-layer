# 可信检索证据层 — Spec

Status: ready-for-agent
Type: feature

## Problem Statement

MoonBit 开发者今天可以用 MoonRetrieve、MoonSearch、vcdb 等包把查询变成候选块，但没有任何可复用的方式回答决定"这段检索结果该不该信"的问题：

- 这个候选块的来源与内容是否足够可信？
- 两篇检索到的文档是否在同一事实上互相矛盾？
- 检索文本里是否嵌入了试图改变模型行为的指令？
- 哪些证据应该先进入生成器，以及如何标注引用？

当前每个应用都要自己重写一套临时启发式。这些逻辑重复、无测试、无法向评审解释，而且默认不安全。MoonBit 生态在这里恰好是空白：重排、证据信任评分、多文档冲突检测、prompt-injection 检测四项均无专门实现。

## Solution

一个确定性、离线、可解释的 MoonBit 库，位于任意检索器与生成器之间。它接受与检索器无关的候选块契约，依次完成风险扫描、信任评分、冲突检测、信任感知重排，输出带引用与风险标注的证据上下文，以及机器可读的报告。不调用模型、不需要密钥、不访问网络。

## User Stories

1. As a RAG 应用开发者, I want 把检索器输出直接接入信任层, so that 我不必在每个项目里重写安全与信任逻辑。
2. As a RAG 应用开发者, I want 信任层接受与检索器无关的候选块契约, so that 我可以继续使用 MoonRetrieve、MoonSearch、vcdb 或自己的检索器。
3. As a RAG 应用开发者, I want 得到重排后的证据列表, so that 最可信的证据先进入生成器。
4. As a RAG 应用开发者, I want 每个候选块带有分项可查的信任评分, so that 我可以调权重而不是靠猜。
5. As a RAG 应用开发者, I want 看到哪些信号抬高或压低了某个块, so that 我能排查误报。
6. As a RAG 应用开发者, I want 跨文档冲突以显式配对的形式报告, so that 我可以展示争议而不是静默选一个。
7. As a RAG 应用开发者, I want 冲突检测覆盖数值、日期、百分比与单位, so that 不依赖模型也能抓到事实不一致。
8. As a RAG 应用开发者, I want 每个候选块都被扫描是否含嵌入指令, so that 检索文本无法劫持提示词。
9. As a RAG 应用开发者, I want 注入发现按规则逐条解释, so that 我可以为隔离决策给出依据。
10. As a RAG 应用开发者, I want 隔离策略可配置（丢弃、标记或降权）, so that 信任层适配不同风险偏好。
11. As a RAG 应用开发者, I want 在令牌预算内组装证据上下文, so that 我能控制提示词大小。
12. As a RAG 应用开发者, I want 每条组装后的证据都带来源引用, so that 最终答案可审计。
13. As a RAG 应用开发者, I want 机器可读的 JSON 报告, so that 我能在 CI 中记录、对比与审计。
14. As a RAG 应用开发者, I want 相同输入产生完全确定的输出, so that 快照测试稳定。
15. As a RAG 应用开发者, I want 可配置的权重与阈值, so that 我能按精度或召回偏好调优。
16. As a RAG 应用开发者, I want 离线运行且不需要密钥, so that CI 与内网环境可用。
17. As a RAG 应用开发者, I want 对中英文文本做合理处理, so that 语料无需额外 NLP 依赖即可工作。
18. As a RAG 应用开发者, I want 在大量候选块上有界的内存与时间开销, so that 生产环境安全。
19. As a RAG 应用开发者, I want 一个批量扫描的 CLI, so that 我不写代码也能评估语料。
20. As an 评测者, I want 在固定语料上看到"有/无信任层"的对比, so that 我知道信任层改变了什么。
21. As a 安全审阅者, I want 注入规则及其边界被明确记录, so that 我知道它抓不到什么。
22. As a 安全审阅者, I want 信任评分的定义精确, so that 它不会被误解为事实正确性或模型置信度。
23. As a 包使用者, I want 库以 SemVer 发布到 mooncakes, so that 依赖管理是标准流程。
24. As a 包使用者, I want 可运行的示例与 README, so that 上手只需几分钟。
25. As a 维护者, I want fixture 驱动的测试与 CI, so that 回归在发布前被抓住。
26. As a 下游生成器, I want 证据上下文是带稳定引用标记的纯文本, so that 任何模型都能消费。
27. As an 最终用户, I want 答案引用来源并披露冲突证据, so that 我能自己判断可信度。

## Implementation Decisions

- **包结构**：一个库包 + 一个 CLI 可执行包。工作名"可信检索证据层"；最终 mooncakes 包名在发布前对注册表查重后确定。注意：`moon-evidence` 与既有 `starlittle/MoonEvidence` 语义冲突，应避开。
- **输入契约**：候选块 = id、文本、来源元数据（uri / 标题 / 获取时间 / 可选信任提示）、检索分数、可选原文区间。契约可 JSON 序列化，与具体检索器无关。
- **输出契约**：报告 = query、配置快照、排序后的证据（id、最终分、信任分及分项、风险发现、冲突引用）、冲突列表（成对的 claim key 与值）、证据上下文（文本 + 引用 + 标注）、诊断信息。
- **管线顺序**：风险扫描 → 信任评分 → 冲突检测 → 重排 → 上下文组装。每一阶段是纯函数且确定性；阶段结果全部进入报告，供观测与调试。
- **风险扫描**：基于规则与信号——祈使式指令、角色/标记 token、隐藏或零宽字符、编码载荷、外泄短语、分隔符逃逸。每条发现 = 规则 id + 严重度 + 文本区间 + 解释。
- **信任评分**：加权分项——来源元数据质量、内容信号（长度、模板化比例、语言一致性）、与其他证据的一致性（冲突惩罚）、风险惩罚。归一到 0..1，附分项明细。它是可解释分数，不是概率。
- **冲突检测**：按显式 subject 抽取 claim（subject 来自元数据键或查询锚定词），值类型为数值、日期、百分比、单位；按 (subject, unit) 分组并报告不相容取值。不做逻辑矛盾证明，不做基于模型的 NLI。
- **重排**：检索分数（批次内条件归一化后）、信任分、冲突惩罚、风险惩罚的加权组合，叠加基于确定性 token 重叠相似度的多样性（MMR 式）；并列时按候选 id 稳定排序。整批检索分已在 [0,1] 时原样使用，否则 min-max 到 [0,1]；报告同时暴露 `retrieval_normalized`。
- **上下文组装**：在令牌预算下贪心选择；使用近似令牌估算（ASCII 按词、CJK 按字）；引用标记 `[n]`；每条引用附来源；末尾附风险与冲突附录。
- **CLI**：`scan` 子命令读取候选 JSON 与 query，写出报告 JSON；当配置为阻断且存在高严重度风险时返回非零退出码。
- **配置**：权重、阈值、预算、隔离策略、启用的规则集；可序列化，并在报告中回显。
- **确定性**：报告中不写墙钟时间戳；顺序稳定；不使用随机数。
- **编译目标**：CLI 与文件 I/O 使用 native；核心管线为纯计算，可编译到 wasm-gc / js。不依赖 `moonbitlang/async`。
- **打包**：Apache-2.0、SemVer、`.moonignore`、CI 使用官方安装脚本；发布到 mooncakes。
- **遵循 ADR**：ADR-0001（补位层，检索器无关）、ADR-0002（全确定性启发式，无模型推理）。

## Testing Decisions

- **好测试的标准**：只挂在两个 seam 上（公共 API、CLI），只断言外部行为——排序结果、评分分项、风险发现、冲突配对、引用、预算遵守——不断言内部函数或私有结构。
- **被测模块**：四个阶段全部通过公共 API 的端到端 fixture 观测；不为 `risk` / `trust` / `conflict` 单独开公共子 API。
- **fixture 语料**：三组——(a) 干净证据；(b) 数值/日期冲突；(c) 注入指令与隐藏字符。每组附预期报告快照。另加两组适配 fixture：合成检索器输出、MoonRetrieve 格式输出。
- **确定性测试**：同一输入运行两次，JSON 字节完全一致。
- **边界测试**：空候选、单候选、重复 id、超预算上下文、缺失元数据、中英混排。
- **CLI 测试**：对固定 fixture 运行后做 `inspect` 快照；验证阻断风险的退出码。
- **性质测试**：信任分恒在 [0,1]；重排结果是输入 id 的排列；上下文中的引用总能解析到已包含证据；预算永不被突破。
- **先例**：作者自己的 `moon-npy` 采用"fixture 语料 + 跨语言 oracle"的验证方式，本项目复用这一思路（固定语料 + 预期输出），不复用其代码；评测指标风格参考 MoonRetrieve 的离线评测。
- **覆盖率**：`moon test --enable-coverage`，覆盖核心路径，不以百分比作为目标。

## Out of Scope

- 检索本身：切分、BM25、向量/ANN 索引、RRF 融合（ADR-0001）。
- 嵌入生成或任何模型推理（ADR-0002）。
- LLM 调用、API 密钥、网络 I/O。
- 内容审核、毒性/有害性分类、事实真伪判定。
- 逻辑矛盾证明或 claim 级蕴含判断。
- Web UI / 仪表盘。
- 持久化、索引、缓存层。
- 多租户鉴权或服务化部署。
- 中英文之外的语种启发式。

## Further Notes

- **赛事硬约束**：单人、一个月窗口、4,000–10,000 行有效 MoonBit、发布 mooncakes、使用 CI、报名前仓库 ≥10 个有效 commits、申报书人工撰写且含至少 3 个使用场景。
- **申报书可用的三个使用场景**：(1) 企业知识库问答，必须披露互相冲突的制度条款；(2) Agent 工具网关，必须隔离被注入的网页内容；(3) 离线评测流水线，对比"有/无信任层"的检索质量。
- **验收演示**：CLI 跑固定语料，输出"有/无信任层"对比表——暴露的不安全块、发现的冲突、拦截的注入、排名变化——并给出可复现命令。
- **调研依据**：截至 2026-11-06，重排 / 信任评分 / 冲突检测 / 注入检测四项确认空白；方法与局限记录在 `research/04-candidate-directions-dedup.md`。申报书中的查重表述应写"检索范围 + 判定口径"，不做绝对断言。
- **命名**：发布前必须在 mooncakes 查重；避开与 `starlittle/MoonEvidence` 的语义混淆。
